# PROMPT_STANDARD

**Статус:** Active  
**Область:** все промпты и рабочие задания, которые человек передаёт ИИ-инструментам (Cursor, ChatGPT, Claude, Codex и др.) в контуре AI POS; системные правила агента в `.cursor/rules/` и `CURSOR_START.md`.  
**Приоритет:** подчиняется `Governance/CONSTITUTION.md`; при конфликте с удобством промпта действует Конституция.  
**Связь:** `Standards/README.md`, `Standards/DEVELOPMENT_STANDARD.md`, `Standards/UX_RULES.md`, `Standards/REVIEW_STANDARD.md`, `Governance/CHANGE_PROTOCOL.md`, `Governance/PIPELINE.md`, рабочее задание в UI (`buildAssignment` / Action Gate).

Этот стандарт **не создаёт** новых ролей, журналов, API или сущностей знаний. Он фиксирует уже действующую практику подготовки и передачи промптов.

---

## 1. Назначение

Промпт в AI POS — это способ **передать согласованную задачу модуля** исполнителю-ИИ с понятными границами, а не способ переписать проект или Конституцию.

Стандарт отвечает на вопросы:

- что обязательно должно быть в промпте;
- чего в промпте быть не должно;
- в каком порядке человек и ИИ работают до изменений в коде;
- как промпт связан с иерархией проект → модуль → задача.

---

## 2. Определения (без новых сущностей)

| Термин | Смысл в этом стандарте |
|--|--|
| **Промпт** | Текст, который человек передаёт ИИ (вставка, чат, агент). |
| **Рабочее задание** | Каноническая форма промпта задачи, собираемая в UI AI POS и копируемая после Action Gate. |
| **Системные правила агента** | Постоянные инструкции в `CURSOR_START.md` и `.cursor/rules/` — не заменяют рабочее задание конкретной задачи. |
| **Action Gate (UI)** | Контроль перед копированием задания: человек подтверждает границы задачи. Не путать с Governance Action Gate для Accepted-решений (`CHANGE_PROTOCOL.md`), хотя принцип тот же: ИИ не закрывает подтверждение единолично. |

---

## 3. Иерархия истины в промпте

Обязательное правило (уже в рабочем задании UI и Конституции, принцип 10 и Layered Knowledge):

1. **Проект** — весь продукт.  
2. **Модуль** — часть продукта.  
3. **Текущая задача** — согласованный объём работы внутри модуля.

Запрещено:

- называть модуль проектом;
- расширять задачу до «всего продукта» без отдельного решения человека;
- подменять Workflow (модуль/задача) выводами System (стадия с диска) или наоборот;
- просить ИИ единолично закрыть Governance Action Gate / Accepted / CONFIRMED-стадию.

Passport / Workflow / System в промпте, если упоминаются, **маркируются раздельно**. System-данные (этап, analysis) не выдаются за постановку задачи человеком.

---

## 4. Когда какой промпт использовать

| Ситуация | Что использовать |
|--|--|
| Выполнение текущей задачи модуля в инструменте | **Рабочее задание** из AI POS (вкладка «Рабочее задание» / копирование с Gate) |
| Старт сессии агента в репозитории AI POS | `CURSOR_START.md` + `.cursor/rules/` + этот стандарт |
| Значимое изменение Freeze / Governance | Не «свободный промпт», а цикл `PIPELINE` / `CHANGE_PROTOCOL`; промпт только помогает Draft, не закрывает Gate |
| Косметический вопрос вне задачи | Короткий уточняющий промпт; **не** копировать полное рабочее задание без нужды |

---

## 5. Обязательная структура рабочего задания

Рабочее задание, передаваемое ИИ для выполнения задачи, должно содержать блоки в этом порядке (как в UI `buildAssignment`):

1. **Заголовок** — для какого инструмента задание.  
2. **Контроль перед передачей задачи** — явное указание, что это требование порядка работы, а не техническая блокировка инструмента.  
3. **Перед началом работы** — прочитать контекст; кратко подтвердить понимание; **не начинать изменения до «+»**; после «-» остановиться.  
4. **Проект** — название, идея, результат, аудитория, активы, ограничения, материалы.  
5. **Модуль** — название, назначение, статус, ограничения (или явный запрет работать без модуля).  
6. **Текущая задача** — название, зачем сейчас, подзадача, референсы.  
7. **Цель**  
8. **Что готово**  
9. **Что сделать**  
10. **Ограничения** — что можно / что нельзя менять.  
11. **Критерии проверки результата**  
12. **Где выполнять** — рабочая папка, инструмент, зачем инструмент, стиль работы инструмента.  
13. **Ожидаемый результат** — результат **задачи**, не всего проекта.  
14. **Формат ответа** — подтверждение уровней → границы → выполнение → проверка.

Если модуля или задачи нет, промпт обязан это сказать и **не** подталкивать к работе «по всему проекту».

---

## 6. Обязательный порядок работы с ИИ

### 6.1. До изменений в файлах

ИИ обязан:

1. Прочитать проект / модуль / задачу / ограничения.  
2. Кратко ответить:
   - что понял;
   - какие области или файлы планирует менять;
   - что менять не будет;
   - как проверит результат.  
3. **Ждать символ «+»** от человека.  
4. После «-» — остановиться и ждать новых указаний.

### 6.2. После «+»

1. Подтвердить **проект / модуль / задачу** раздельно.  
2. Перечислить, что не будет менять.  
3. Выполнить **только** текущую задачу.  
4. Показать результат и проверку по критериям.  
5. Соблюдать `DEVELOPMENT_STANDARD` (в т.ч. изоляция коммита, если просят коммит).

### 6.3. Человек

- Носитель подтверждения («+» / Action Gate UI / Governance Gate).  
- Не обязан принимать первый план ИИ.  
- Может сузить область до начала правок.

### 6.4. Approval Freeze (Режим после утверждения)

После явного утверждения пользователем архитектуры, UX/UI, структуры, сценариев, названий или любых других проектных решений ИИ обязан перейти в режим реализации.

Все утверждённые решения считаются зафиксированными.

Запрещено:
- пересматривать утверждённые решения по собственной инициативе;
- предлагать новые концепции или варианты;
- возвращать обсуждение к уже утверждённым вопросам;
- изменять согласованную концепцию без прямого запроса пользователя.

Разрешено:
- реализовывать утверждённое решение;
- исправлять ошибки реализации;
- предлагать улучшения, не изменяющие утверждённую концепцию.

Пересмотр утверждённых решений допускается только по инициативе пользователя.

При этом данное правило относится к поведению ИИ в процессе работы и не заменяет Governance Architecture Freeze, описанный в ADR-0002.

## 7. Правила содержания промпта

### Обязательно

- Явные границы «можно / нельзя».  
- Рабочая папка, если работа идёт в файлах.  
- Критерии проверки, измеримые для задачи.  
- Одна текущая задача (одна логическая цель).  
- Указание инструмента, если оно влияет на стиль ответа.

### Запрещено

- Просить обойти Конституцию, Freeze, Pipeline или Review «для скорости».  
- Смешивать несколько несвязанных задач в одном рабочем задании.  
- Включать секреты, токены, пароли.  
- Подменять факты диска (System) ручными утверждениями без пометки источника.  
- Требовать от ИИ «утвердить» стадию проекта или Health Accepted.  
- Раздувать промпт полными копиями репозитория, если достаточно пути и списка файлов/референсов.

### Рекомендуется

- Минимальный достаточный контекст (как в `CURSOR_START`: минимум токенов).  
- Явный список «не трогать».  
- Для UI — отсылка к `UX_RULES` / `DESIGN_SYSTEM`, без пересказа всей дизайн-системы.  
- Для документации Standards/Governance — править существующий файл, не плодить дубликаты (`Standards/README.md`).

## 8. Системные правила агента vs рабочее задание

| Слой | Где живёт | Роль |
|--|--|--|
| Конституция | `Governance/CONSTITUTION.md` | Высшие нормы |
| Стандарты | `Standards/*` | Предметные правила, включая этот файл |
| Старт сессии | `CURSOR_START.md`, `.cursor/rules/` | Постоянный ритуал: анализ → план → «+» → работа → отчёт |
| Задача | Рабочее задание UI | Конкретный объём изменений |

Конфликт: действует Конституция, затем Standards по приоритету из `Standards/README.md`, затем уточнения `.cursor/rules/` (они не могут противоречить Конституции).

Системные правила **не заменяют** блоки ПРОЕКТ / МОДУЛЬ / ЗАДАЧА в рабочем задании.

---

## 9. Промпты вне UI (ручные)

Если человек пишет промпт вручную (без копирования из AI POS), он всё равно обязан сохранить:

- раздельность проект / модуль / задача;  
- ожидание «+» перед правками в репозитории AI POS и подконтрольных проектах;  
- запрет расширения области без явного согласия;  
- критерии проверки.

Ручной промпт не обязан дословно повторять все 14 блоков, если задача тривиальна (один файл, одна правка), но **не может** нарушать разделы 3, 6 и 7.

---

## 10. Проверка качества промпта (перед копированием)

Человек перед передачей ИИ проверяет:

- [ ] Понятны проект, модуль и текущая задача по отдельности.  
- [ ] Есть «можно» и «нельзя».  
- [ ] Есть ожидаемый результат задачи и критерии проверки.  
- [ ] Указана рабочая папка (для файловых изменений).  
- [ ] Нет второй скрытой задачи в том же тексте.  
- [ ] Нет просьбы обойти Governance / Freeze.  
- [ ] Промпт соответствует User First: ИИ понимает, что происходит и что делать дальше (`UX_RULES.md`).

ИИ перед началом правок проверяет то же в своём кратком подтверждении.

---

## 11. Связь с Review и коммитом

- После выполнения — проверка по критериям задания; замечания человека не закрываются самооценкой ИИ (Конституция, принцип 3).  
- Коммит — по `DEVELOPMENT_STANDARD` (один коммит = одна логическая задача; изоляция WIP).  
- Промпт «сделай коммит» не отменяет требования к сообщению коммита и к отсутствию посторонних файлов.

## 12. Примеры

### 12.1. Допустимое начало ответа ИИ (до «+»)

```text
Понял:
- Проект: «Мой день»
- Модуль: «Историческая справка»
- Задача: механика раскрытия карточки на трёх датах

Планирую менять: только файлы модуля исторической справки в рабочей папке.
Не буду менять: погоду, календарь, общую архитектуру главной без отдельного решения.

Проверка: карточка раскрывается на трёх датах, без ошибок в консоли.

Жду «+» для начала правок.
```

### 12.2. Недопустимо

```text
Сделаю рефакторинг всего приложения «Мой день» и заодно обновлю архитектуру AI POS.
Стадию проекта ставлю EXECUTION сам. Коммитну всё подряд.
```

## Минимально достаточный промпт (Minimum Sufficient Prompt)

### Назначение

Этот раздел определяет, как ИИ должен интерпретировать промпты пользователя.

Цель — уменьшать объём рабочих промптов по мере накопления знаний проекта и развития стандартов.

### Принцип

Промпт должен быть настолько коротким, насколько это возможно, но достаточным для однозначного понимания задачи.

Цель промпта — не пересказать проект, а сообщить ИИ только новую задачу или новое ограничение.

### Правила

- Не ожидать повторения уже известных правил и контекста проекта.
- Не требовать повторного описания действующих стандартов, архитектурных решений и ранее принятых правил.
- Не ожидать перечисления действий, которые уже являются обязательными по стандартам проекта.
- Один промпт — одна задача.
- Если задача понятна, считать короткий промпт предпочтительным.
- Если информации недостаточно, задать минимально необходимый уточняющий вопрос, а не ожидать более длинный промпт.

### Принцип доверия

После принятия стандарт становится обязательной частью рабочего контекста ИИ и применяется автоматически до его изменения или отмены.

Если пользователь специально не отменил правило, считается, что все утверждённые стандарты продолжают действовать.

### Хороший пример

❌ Избыточно

Покажи состав изменений, оцени риски, перечисли зависимости, ничего не меняй, не коммить, дождись моего решения...

✅ Достаточно

Покажи состав изменений, предложи безопасный план и жди моего решения.

### Критерий качества

Хороший промпт не описывает уже известное.

Хороший промпт сообщает ИИ только то, чего он ещё не знает.

Чем зрелее проект и полнее стандарты, тем короче должны становиться рабочие промпты.

## 13. Изменение этого стандарта

Значимое изменение правил промптов (смена Gate-порядка, отмена иерархии, право ИИ начинать без «+») — через `CHANGE_PROTOCOL` / Pipeline, не «тихим» PR.

Уточнение формулировок без смены смысла — допустимо как правка Active-стандарта при сохранении согласованности с UI рабочего задания.

## Architecture Research

Раздел **не является действующей нормой** Prompt Standard. Здесь фиксируются проблемы вне рамок одного только текста стандарта.

Открытые пункты ниже **не исправлялись** этим документом. Закрытые помечены явно.

### AR-PS-01. Расхождение Конституции и `.cursor/rules/ai-pos-constitution.mdc` — **CLOSED**

**Статус:** закрыт коммитом `676e07c` (`fix: sync Cursor constitution rule with principle 11`).  
**Было:** в каноне принципы 1–11; в `.cursor/rules/ai-pos-constitution.mdc` — «ровно 10» и перечень 1–10.  
**Стало:** rule синхронизирован с `Governance/CONSTITUTION.md` (ровно 11 принципов, включая Layered Knowledge Principle).  
**Проверка:** заголовки и текст принципа 11 совпадают с каноном.

### AR-PS-02. Нет автоматической связи UI-шаблона и стандарта

**Статус:** открыт.  
**Суть:** нормативная структура рабочего задания описана здесь; фактическая сборка текста — в UI (`buildAssignment`). При расхождении «стандарт vs кнопка копирования» единый механизм сверки отсутствует.  
**Почему не чинится здесь:** потребовался бы новый процесс синхронизации или генерация задания из стандарта — новая сущность/контур.  
**Риск:** стандарт Active, а скопированный текст устареет относительно стандарта (или наоборот).

### AR-PS-03. Organization/ROLES и владельцы промптов не определены

**Статус:** открыт.  
**Суть:** стандарт говорит «человек подтверждает», но `Organization/ROLES.md` и матрица ответственности пусты.  
**Почему не чинится здесь:** заполнение Organization — отдельный контур, не часть Prompt Standard.  
**Риск:** неочевидно, кто обязан проводить UI Action Gate vs кто пишет ручные промпты.

### AR-PS-04. DOCUMENT_STANDARD пуст

**Статус:** открыт.  
**Суть:** долгие шаблоны промптов-документов (если хранить вне UI) не имеют правил оформления документов.  
**Почему не чинится здесь:** это область `DOCUMENT_STANDARD.md`, сейчас Empty/Draft.  
**Риск:** копирование больших промптов в произвольные MD без единого оформления.

### AR-PS-05. Два смысла «Action Gate»

**Статус:** открыт.  
**Суть:** одинаковое имя для UI-контроля перед копированием задания и для Governance Gate перед Accepted.  
**Почему не чинится здесь:** переименование — изменение UX/Governance терминологии (Organization/Glossary пуст). Стандарт лишь фиксирует различие.  
**Риск:** в промптах и чатах люди/ИИ путают «подтверди Gate» (задача) с «Accepted Freeze».
