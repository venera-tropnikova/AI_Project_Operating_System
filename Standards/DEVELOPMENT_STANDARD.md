Правила разработки и внесения изменений в кодовую базу и репозиторий.

# Git Commit Standard

Это **глобальный** стандарт Git. Он обязателен для всех проектов пользователя, а не только для AI POS.

## Основной принцип

Один коммит = одна логическая задача.

В коммит нельзя включать:

- несвязанные изменения;
- незавершённый WIP другой задачи;
- временные файлы;
- сторонние документы;
- изменения, которые не относятся к цели коммита.

Если рабочая директория содержит смешанные изменения, перед коммитом их нужно изолировать.

## Разделение логических задач перед коммитом

Если в рабочем дереве обнаружены незакоммиченные изменения, относящиеся к нескольким логическим задачам, ИИ обязан:

- сообщить об этом пользователю;
- определить предполагаемые границы логических задач;
- предложить безопасный план разделения изменений;
- дождаться решения пользователя.

Самостоятельно объединять изменения нескольких логических задач в один коммит запрещено.

При необходимости ИИ может временно восстановить промежуточные состояния, проверить их работоспособность и только после этого подготовить отдельные коммиты. Итоговое состояние рабочего дерева должно полностью совпадать с исходным состоянием до начала разделения.

## Заголовок коммита

Формат:

```text
<type>(optional-scope): <краткое описание на английском>
```

Использовать Conventional Commits:

- `feat` — новая функциональность;
- `fix` — исправление ошибки;
- `refactor` — изменение структуры без изменения поведения;
- `docs` — документация;
- `test` — тесты;
- `perf` — оптимизация;
- `style` — оформление без изменения логики;
- `chore` — служебные изменения.

Заголовок должен:

- быть кратким;
- описывать конкретный результат;
- быть понятным в `git log --oneline`;
- не использовать сообщения вроде:
  - `update`;
  - `changes`;
  - `various fixes`;
  - `small fixes`;
  - `more work`.

К каждому заголовку обязательно готовится **русский перевод** (одна ясная фраза для человека).

## Тело значимого коммита

Все значимые коммиты обязаны иметь подробное описание, чтобы через годы по истории репозитория было легко понять, что и зачем сделано.

Обязательные разделы тела:

```text
Project:
<название проекта>

Milestone:
<направление или крупный этап>

Stage:
<номер или название этапа, если есть; иначе «—»>

Purpose:
<зачем выполнено изменение>

Added:
- ...

Changed:
- ...

Not changed:
- ...

Testing:
- ...

Known limitations:
- ...

Next step:
- ...
```

Раздел без содержания заполнять явно (`нет` / `—`), а не опускать молча для значимых коммитов.

Дополнительный раздел `Related:` допускается, но не заменяет обязательные разделы выше.

## Обязательные ответы коммита

Из сообщения должно быть понятно:

- что сделано;
- зачем это сделано;
- какие части изменены;
- какие части сознательно не менялись;
- как результат проверен;
- какие ограничения остались;
- что является следующим шагом, если это важно.

## Контрольная точка после задачи

После завершения и проверки каждой **логической задачи** ИИ обязан:

1. Проверить `git status`.
2. Определить, образует ли результат отдельный завершённый коммит.
3. Сообщить о незакоммиченных изменениях (если они есть).
4. Спросить пользователя: «Задача завершена. Подготовить коммит?»

Если накопились изменения **разных** логических задач:

- не объединять их в один коммит;
- предложить безопасное разделение по задачам;
- дождаться решения пользователя.

Не применять эту контрольную точку:

- после промежуточных правок;
- при незавершённой работе;
- в середине многошаговой задачи до итоговой проверки.

Коммит выполнять только после явного подтверждения пользователя (см. ниже).

## Порядок работы Cursor / ИИ

### Перед коммитом (обязательно показать пользователю)

1. Проверить `git status` и убедиться, что коммит содержит только одну логическую задачу.
2. Показать:
   - изменённые файлы;
   - что **войдёт** в коммит;
   - что **не войдёт** в коммит;
   - название коммита (заголовок);
   - русский перевод названия;
   - полное описание тела:
     - Project;
     - Milestone;
     - Stage;
     - Purpose;
     - Added;
     - Changed;
     - Not changed;
     - Testing;
     - Known limitations;
     - Next step.
3. При необходимости показать diff/stat по файлам, входящим в коммит.

### Подтверждение

Выполнять коммит **только после явного подтверждения пользователя**.

Без подтверждения коммит создавать нельзя, даже если пользователь ранее просил «подготовить коммит».

### После коммита (обязательно показать)

1. hash;
2. название коммита;
3. русский перевод названия;
4. какие файлы вошли в коммит;
5. `git status`;
6. статус push: **выполнен** / **не выполнен**.

Push выполнять только по отдельной явной просьбе пользователя.

## Проверка

Для функциональных изменений по возможности указывать:

- Browser smoke PASS;
- JS errors: [];
- lint / tests PASS;
- название проверенного проекта или сценария.

Нельзя писать PASS, если проверка фактически не выполнялась.

## Пример

```text
feat(ui): redesign existing project connection flow

Project:
AI Project Operating System

Milestone:
Project Connection UX

Stage:
—

Purpose:
Упростить сценарий подключения существующего проекта и убрать лишние действия пользователя.

Added:
- единый экран подключения;
- кнопка «Список проектов»;
- результат проверки на той же странице.

Changed:
- удалён отдельный экран результата;
- упрощён интерфейс подключения;
- улучшена композиция элементов.

Not changed:
- Bridge API;
- логика анализа проекта;
- сценарий открытия проекта.

Testing:
- сценарий нового проекта;
- сценарий уже подключённого проекта;
- навигация к списку проектов.

Known limitations:
- нет.

Next step:
Переработка рабочего пространства проекта («Обзор проекта»).
```

Русский перевод заголовка:

```text
UI: переработан сценарий подключения существующего проекта
```

## Область действия

Правило обязательно для **всех** проектов:

- AI POS;
- проект «Мой день»;
- любые другие текущие и новые репозитории пользователя;
- работа через Cursor и другие ИИ-инструменты.

Локальные правила отдельного репозитория не могут ослаблять этот стандарт; они могут только уточнять предметные детали проекта.
