# Git Commit Standard

## Основной принцип

Один коммит = одна логическая задача.

В коммит нельзя включать:

- несвязанные изменения;
- незавершённый WIP другой задачи;
- временные файлы;
- сторонние документы;
- изменения, которые не относятся к цели коммита.

Если рабочая директория содержит смешанные изменения, перед коммитом их нужно изолировать.

## Заголовок коммита

Формат:

```text
<type>: <краткое описание>
```

Использовать Conventional Commits:

- `feat` — новая функциональность;
- `fix` — исправление ошибки;
- `refactor` — изменение структуры без изменения поведения;
- `docs` — документация;
- `test` — тесты;
- `perf` — оптимизация;
- `style` — оформление без изменения логики;
- `chore` — служебные изменения.

Заголовок должен:

- быть кратким;
- описывать конкретный результат;
- быть понятным в `git log --oneline`;
- не использовать сообщения вроде:
  - `update`;
  - `changes`;
  - `various fixes`;
  - `small fixes`;
  - `more work`.

## Тело значимого коммита

Для этапов, функций, архитектурных изменений и исправлений обязательно подробное тело:

```text
Project:
<название проекта>

Milestone:
<направление или крупный этап>

Stage:
<номер или название этапа, если есть>

Purpose:
<зачем выполнено изменение>

Added:
- ...

Changed:
- ...

Not changed:
- ...

Testing:
- ...

Related:
- ...

Known limitations:
- ...

Next step:
- ...
```

Разделы без содержания можно не добавлять.

## Обязательные ответы коммита

Из сообщения должно быть понятно:

- что сделано;
- зачем это сделано;
- какие части изменены;
- какие части сознательно не менялись;
- как результат проверен;
- какие ограничения остались;
- что является следующим шагом, если это важно.

## Порядок работы Cursor

Перед созданием каждого значимого коммита Cursor обязан:

1. Проверить `git status`.
2. Убедиться, что коммит содержит только одну логическую задачу.
3. Показать пользователю:
   - заголовок;
   - полное тело коммита;
   - список файлов;
   - diff/stat.
4. Не создавать коммит до подтверждения пользователя, если пользователь заранее не дал явное разрешение на коммит.
5. После подтверждения создать коммит.
6. После коммита показать:
   - hash;
   - итоговый заголовок и body;
   - diff/stat;
   - результаты тестов или smoke;
   - `git status`.

## Проверка

Для функциональных изменений по возможности указывать:

- Browser smoke PASS;
- JS errors: [];
- lint / tests PASS;
- название проверенного проекта или сценария.

Нельзя писать PASS, если проверка фактически не выполнялась.

## Пример

```text
feat: show system attention in overview

Project:
AI POS

Milestone:
Overview Read Model

Stage:
4

Purpose:
Display system attention separately from Workflow Review.

Added:
- System Attention block
- needs_attention rendering
- blocked and invalid states
- freshness synchronization

Changed:
- renderOverview
- finishCliRender
- freshness ticker

Not changed:
- Passport
- Workflow Review
- work-desk
- Health documents

Testing:
- Browser smoke PASS
- JS errors: []
- Project “Мой день” verified

Related:
- OVERVIEW_READ_MODEL.md
```
