# AI POS — Architecture Risks and Decisions

**Статус:** проектные решения по критическим рискам  
**Дата:** 2026-07-26  
**Область:** только пять вопросов ниже  
**Вне области:** переписывание Project Intake & Discovery, Project Health, UI-прототипа; реализация и код

Этот документ **не заменяет** существующую архитектуру.  
Он фиксирует решения там, где независимое ревью выявило пробелы управления, независимости подтверждений и масштабирования записей.

## 1. Операционное определение независимого подтверждения  
### (команда: один человек + несколько ИИ)

### Проблема

В классическом смысле «независимая проверка» предполагает разных людей.  
В AI POS часто работает **один человек** и несколько ИИ-ролей. Без явного определения легко принять за подтверждение:

- повтор того же ИИ;
- согласие человека без осмотра артефакта;
- «галочку» в интерфейсе без доказательства.

Тогда контроль (Action Gate, Review, Health) становится формальным.

### Принятое архитектурное решение

**Независимое подтверждение** — это согласие, опирающееся на **иной источник доказательства**, чем тот, который создал спорный результат.

#### Что считается независимым источником

| Источник | Считается независимым | Условие |
|---|---|---|
| Человек-оператор после осмотра артефакта | Да | Есть явная отметка осмотра (чек-лист / «видел результат») |
| Другая ИИ-роль с другой целью | Да, как *вспомогательное* | Роль не совпадает с исполнителем (например QA ≠ Разработчик) и опирается на критерии проверки |
| Внешний факт системы | Да | Существование файла, дата изменения, статус delivery evidence, результат сверки scope и т.п. |
| Повторный прогон **другого** инструмента по тем же критериям | Да, как *второе доказательство* | Инструмент и/или роль иные; критерии те же |

#### Что не считается независимым источником

- тот же исполняющий ИИ, подтверждающий свою работу;
- другая «роль» в промпте, но тот же непрерывный диалог без смены задачи/критериев;
- автоматическая галочка по умолчанию;
- подтверждение человека без осмотра («просто нажал Принять»);
- пересказ результата исполнителем без обращения к артефакту;
- Project Health / статус инструмента как замена проверки результата.

#### Когда достаточно одного доказательства

Достаточно **одного** независимого подтверждения, если одновременно:

1. изменение в пределах замороженного scope;
2. задача не затрагивает защищённые области и Delivery «опубликовано/отдано»;
3. чек-лист проверки результата полностью отмечен человеком;
4. нет сигнала Health уровня «есть критические проблемы» по связанным индикаторам.

Типичный случай: обычная текущая задача модуля, принимает человек после чек-листа.

#### Когда нужны два доказательства

Нужны **два** независимых доказательства, если верно хотя бы одно:

1. затрагиваются защищённые области / правила проекта требуют отдельного решения;
2. это экстренное изменение (см. раздел 2) — пост-фактум;
3. меняется Delivery-артефакт, уже заявленный как отправленный/опубликованный;
4. принимается результат при неполном автоматическом контроле (много `unknown`);
5. человек совмещает роли «исполнитель постановки» и «принимающий», а работу делал ИИ — тогда вторым доказательством служит **внешний факт** (артефакт + сверка scope / наличие файла / отсутствие запрещённых путей), а не второй ИИ обязательно.

Модель для соло-оператора:

```text
Доказательство A: человек + чек-лист осмотра
Доказательство B: системный факт (артефакт / scope_check / delivery evidence)
```

Второй ИИ желателен, но **не обязателен**, если B надёжен.

#### Роль подтверждения пользователя

Человек — **единственный носитель решения о принятии** в соло-режиме.

- ИИ может рекомендовать «принять» / «есть замечания».
- ИИ не может завершить Review статусом «Принято» без человека.
- Подтверждение пользователя имеет силу только вместе с отмеченным чек-листом осмотра (или явным Accepted Risk с причиной и сроком — по политике Health).
- Подтверждение пользователя **не отменяет** необходимость системного факта там, где политика требует двух доказательств.

### Альтернативы

1. Всегда требовать двух ИИ-ролей — тяжело для соло, создаёт иллюзию независимости.  
2. Считать человека всегда достаточным без чек-листа — быстро, но формально.  
3. Полностью доверить accept исполняющему ИИ — неприемлемо для AI POS.

### Риски

- Человек начнёт «принимать пачкой» без осмотра.  
- Смена ярлыка роли ИИ будет выдаваться за независимость.  
- Системный факт будет слишком слабым (только mtime) и создаст ложную уверенность.

### Критерий готовности

- В правилах продукта зафиксированы таблицы «считается / не считается».  
- В Review нельзя поставить «Принято» без чек-листа.  
- Для случаев «нужны два доказательства» в состоянии задачи видно, какое доказательство A/B уже есть.  
- Исполняющий ИИ не имеет права финального accept.

### Решения, требующие нашего подтверждения

1. Является ли второй ИИ (QA) обязательным для *всех* задач или только для классов риска выше?  
2. Какой минимальный системный факт принимаем как доказательство B (mtime/hash, scope_check, ручной список файлов)?  
3. Нужен ли режим «осознанно быстро» с одним доказательством и обязательным пост-review за 24 часа?

## 2. Emergency Change Protocol

### Проблема

Иногда нужно срочно исправить поломку (сайт лежит, презентация завтра утром, документ с критичной ошибкой).  
Обычный цикл «задача → gate → работа → проверка → принятие» может быть слишком медленным.  
Без протокола люди будут обходить правила негласно — и в записях появится ложь.

### Принятое архитектурное решение

Вводится явный **Emergency Change Protocol (ECP)**: временное ускорение с обязательным следом и пост-фактум review.

#### Основания для экстренного изменения

Допустимо только при одном из оснований:

1. **Поломка результата** — нельзя открыть / показать / сдать обязательный артефакт.  
2. **Внешний дедлайн ≤ 24 часов** с подтверждённым обязательством перед кем-то.  
3. **Безопасность / утечка / недопустимый контент** в уже доступном результате.  
4. **Блокировка продолжения всей работы** (например, повреждён единственный рабочий файл).

Не основание:

- «просто хочется быстрее»;
- удобство исполнителя ИИ;
- желание обойти нелюбимую проверку.

#### Кто может инициировать

- Только **человек-оператор проекта** (владелец / текущий ответственный).  
- ИИ может *предложить* ECP, но не включить его сам.

#### Что можно изменить немедленно

Разрешено **минимально достаточное** исправление:

- только зона, необходимая для снятия аварии;
- без расширения scope «заодно»;
- без изменения правил проекта и мастер-стандартов;
- без публикации/отправки нового Delivery, если авария не в delivery-слое (либо только откат/hotfix delivery).

Запрещено под видом ECP:

- новый функционал;
- редизайн «раз уж открыли»;
- смена архитектуры / структуры документа целиком;
- массовые рефакторинги.

#### Какие записи обязательны

В момент инициации (до или сразу после первого изменения, но не позже окончания сессии):

1. `emergency_id`  
2. основание (код из списка выше)  
3. краткое описание аварии  
4. что именно разрешено менять (временный scope)  
5. что менять запрещено  
6. кто инициировал (человек)  
7. timestamp начала  
8. связанные артефакты  

После изменения:

9. что фактически сделано  
10. ссылка на записи Audit / Decision Log  
11. срок пост-фактум review  

#### Срок пост-фактум review

- По умолчанию: **24 часа** с момента закрытия аварийной сессии.  
- Для основания «внешний дедлайн»: не позднее чем через **24 часа после дедлайна**.  
- Просроченный пост-review повышает Project Health до состояния внимания/критичности (по уже спроектированной модели Health), пока review не закрыт.

Пост-review обязан ответить:

- нужно ли оставить изменение;
- нужно ли откатить;
- нужно ли оформить нормальную задачу и обновить правила/scope.

#### Как временное решение становится постоянным или отменяется

```text
ECP change
   ├─► Post-review = KEEP
   │      → создаётся/обновляется нормальная задача-фиксация
   │      → scope/rules обновляются штатно
   │      → emergency закрывается как absorbed
   ├─► Post-review = REVERT
   │      → откат (или компенсирующее изменение)
   │      → emergency закрывается как reverted
   └─► Post-review = SUPERSEDE
          → заменяется штатным решением с новым task/decision
          → emergency закрывается как superseded
```

Временное не становится «тихим постоянным» без KEEP/SUPERSEDE.

### Альтернативы

1. Запретить ECP полностью — чисто, но нереалистично.  
2. Разрешить ИИ включать ECP — опасно.  
3. ECP без пост-review — разрушает смысл правил.

### Риски

- Частый ECP обесценит обычный процесс.  
- Слишком широкий временный scope.  
- Пост-review будут откладывать бесконечно.

### Критерий готовности

- Есть конечный список оснований.  
- Только человек инициирует.  
- Обязательные поля записи определены.  
- Срок пост-review задан.  
- Переходы KEEP / REVERT / SUPERSEDE описаны.  
- Health/Workflow умеют показывать открытый ECP (на уровне будущего UI — вне объёма реализации сейчас).

### Решения, требующие нашего подтверждения

1. Лимит: не более N открытых ECP на проект одновременно (рекомендация: 1)?  
2. Нужно ли запрещать новый обычный Delivery, пока ECP не закрыт?  
3. Достаточно ли 24 часов для соло-режима или сделать 48?

## 3. Независимое создание `task_scope.json`

### Проблема

Если исполняющий ИИ сам пишет границы своей задачи, он может расширить scope в свою пользу.  
Тогда Action Gate и «что нельзя менять» теряют силу.

### Принятое архитектурное решение

Границы задачи создаёт **Scope Builder** — отдельный шаг *до* исполнения.  
Исполняющий ИИ получает уже **замороженный** `task_scope.json` и не является его автором.

#### Scope Builder

Логический модуль (человек + при необходимости ИИ-помощник постановки, **не** исполнитель кода/правок).

Ответственность:

- собрать черновик scope из входных источников;
- показать человеку на подтверждение;
- записать `task_scope.json` в состояние задачи;
- перевести scope в состояние `frozen`.

#### Входные источники Scope Builder

1. Карточка проекта (тип, миссия, правила).  
2. Текущий модуль.  
3. Текст текущей задачи (цель, зачем сейчас, ожидаемый результат).  
4. Правила проекта: защищённые области, запреты, масштаб изменений.  
5. Реестр якорных артефактов.  
6. (Опционально) последний snapshot фактов — только как подсказка путей/файлов, не как право расширять scope.  
7. (Опционально) шаблон scope для Project Type.

Исполняющий ИИ и его черновики правок **не** являются входом Scope Builder.

#### Кто подтверждает scope

- Обязательно: **человек-оператор**.  
- Опционально: ИИ-роль «Архитектор / постановщик» готовит черновик.  
- Исполняющий ИИ: только *читает* frozen scope.

Для соло-режима: человек подтверждает чек-листом «границы верны / запреты верны / критерии проверки включены» (согласовано с уже существующим Action Gate по смыслу).

#### Когда scope считается замороженным

Scope = `frozen`, когда:

1. человек подтвердил scope;
2. записан `scope_version` + timestamp;
3. задача переведена в состояние, допускающее исполнение;
4. хэш/нормализованная копия scope сохранена для сверки.

После `frozen`:

- исполнитель не может менять scope;
- изменение scope = новая версия + новое подтверждение человека;
- копирование рабочего задания использует только frozen scope.

Исключение: Emergency Change Protocol создаёт **временный emergency scope** с отдельной меткой, не подменяя тихо обычный frozen scope.

#### Как `scope_check` сверяет результат

Логика проверки (имя `scope_check.py` — целевой механизм; реализация вне этого документа):

1. Вход: frozen `task_scope.json` + набор фактических изменений (diff путей / список затронутых артефактов / манифест сессии).  
2. Проверки:  
   - все изменённые пути/артефакты ∈ allowed;  
   - ни один ∉ forbidden / protected (если не было отдельного разрешения);  
   - не появились артефакты вне списка, если политика типа проекта это запрещает;  
   - критерии проверки из scope присутствуют в задании/review.  
3. Выход: `pass` / `fail` + список нарушений.  
4. `fail` блокирует «Принято» и повышает внимание Health; не «чинит» автоматически.

Пока нет технической интеграции с Git/FS-diff, допустим режим **манифеста изменений**, заявленного человеком или bridge; отсутствие diff = `unknown`, а не silent pass.

### Альтернативы

1. Исполнитель пишет scope, человек только подписывает — слабее.  
2. Scope только в промпте без файла — нельзя надёжно сверять.  
3. Полный запрет помощи ИИ в черновике scope — безопаснее, но медленнее для соло.

### Риски

- Человек подтвердит слишком широкий scope «на всякий случай».  
- Без bridge сверка будет опираться на честное заявление.  
- Подмена scope_version при отсутствии защиты записи.

### Критерий готовности

- Описан контракт полей `task_scope.json` (минимально: allowed, forbidden, artifacts, acceptance_criteria, version, frozen_at, approved_by).  
- Разделены роли: builder/approver ≠ executor.  
- Определены условия freeze и перевыпуска версии.  
- Определён вход/выход `scope_check` и поведение при fail/unknown.

### Решения, требующие нашего подтверждения

1. Где физически хранить `task_scope.json`: внутри `.ai-pos/tasks/<id>/` или встроено в `project_state`?  
2. Разрешаем ли ИИ-постановщику черновик scope в v1?  
3. Что делать при fail после фактических правок: только блокировать accept или требовать ECP/revert?

## 4. Синхронизация мастер-стандартов AI POS с проектами

### Проблема

У AI POS есть общие стандарты (правила контроля, протоколы, шаблоны).  
В проектах — локальные правила.  
Если копировать стандарты хаотично, локальные правила затрутся или проекты «отстанут» незаметно.

### Принятое архитектурное решение

Разделяем **мастер-стандарты продукта** и **локальные правила проекта**.  
В проект копируются только помеченные к распространению документы/шаблоны; локальные правила никогда не перезаписываются молча.

#### Где находится мастер-версия

Каноническое место (логическая схема):

```text
AI_POS_HOME/
  standards/
    VERSION
    manifest.json
    ... распространяемые документы и шаблоны
```

Пока продукт однофайловый/локальный, `AI_POS_HOME` — каталог установки/репозитория AI POS, не каталог пользовательского проекта.

#### Какие документы копируются в проекты

Копируются **только** элементы с флагом `distributable: true` в манифесте.  
Рекомендуемые классы:

- шаблоны scope;  
- шаблон чек-листа проверки по типу проекта;  
- описание Action Gate / ECP (краткая памятка);  
- шаблон handoff;

Не копируются автоматически:

- персональные правила конкретного проекта;  
- mission/protected modules проекта;  
- Decision/Audit логи;  
- демо-данные.

Локальные правила проекта живут отдельно, например:

```text
.ai-pos/rules/local/     # не перезаписывается синхронизацией
.ai-pos/standards/       # копия/снимок мастер-стандартов
```

#### Как определяется версия

- Файл `standards/VERSION` (semver: `MAJOR.MINOR.PATCH`).  
- `manifest.json` перечисляет файлы, хэши, `min_compatible_schema`.  
- В проекте хранится `standards_pin`: `{ version, synced_at, hashes }`.

Правило совместимости:

- PATCH/MINOR — обычно безопасное обновление шаблонов;  
- MAJOR — требует явного согласия человека (возможны ломающие изменения процесса).

#### Как обнаруживается расхождение

При открытии проекта / периодической проверке:

1. сравнить `standards_pin.version` с мастер-`VERSION`;  
2. сравнить хэши распределённых файлов с манифестом;  
3. статусы: `current` / `update_available` / `modified_locally` / `incompatible`.

`modified_locally` на файлах в `.ai-pos/standards/` означает: пользователь правил копию — обновление не затирает без выбора.

#### Как обновляются проекты без уничтожения локальных правил

Стратегия **merge с защитой локального слоя**:

1. Обновляются только пути `.ai-pos/standards/**` из манифеста.  
2. `.ai-pos/rules/local/**` и поля rules внутри `project_state` не трогаются.  
3. Если шаблон обновился, а проект уже создал производный чек-лист — создаётся `update_offer`, не автозамена.  
4. Пользователь выбирает: принять шаблон / оставить локальное / принять и сохранить backup старого.

#### Что происходит при конфликте

| Конфликт | Поведение |
|---|---|
| Мастер новее, локальные standards не менялись | Предложить обновление; по согласию заменить snapshot standards |
| Мастер новее, локальные standards изменены | Не затирать; показать diff/маркировку конфликта; backup + ручной выбор |
| MAJOR несовместим | Блокировать автообновление; работа проекта продолжается на pinned; показать предупреждение |
| Локальные правила противоречат новому стандарту | Конфликт **не авто-резолвится**; создаётся запись Decision Log + задача «согласовать правила» |

### Альтернативы

1. Всегда держать standards только по ссылке без копий — сложно офлайн/handoff.  
2. Полностью копировать всё всегда — риск затирания.  
3. Никакой синхронизации — быстрый дрейф качества между проектами.

### Риски

- Пользователи правят копии standards вместо local rules.  
- Слишком частые MAJOR.  
- Handoff проекта без `standards_pin` создаст неоднозначность.

### Критерий готовности

- Определены `AI_POS_HOME/standards`, `VERSION`, `manifest`.  
- Разделены `standards` vs `rules/local`.  
- Описаны статусы расхождения и поведение конфликтов.  
- MAJOR требует явного согласия.  
- Локальные правила проекта не входят в автозамену.

### Решения, требующие нашего подтверждения

1. Где физически будет `AI_POS_HOME` на машине пользователя в v1?  
2. Копируем ли standards в каждый проект или только pin + чтение из home (для handoff нужен snapshot)? Рекомендация: pin + snapshot копируемых файлов в проекте.  
3. Кто инициирует обновление: только человек или ещё и мягкое напоминание Health?

## 5. Масштабирование Records  
### Decision Log и Audit Log

### Проблема

Записи решений и аудита быстро растут (задачи, gate, review, ECP, sync standards).  
Без структуры и архивирования поиск деградирует, а «исправление истории» соблазняет удалять неудобные записи.

### Принятое архитектурное решение

Два журнала с разными задачами; записи **не удаляются**, а помечаются `superseded` / архивируются.

#### Структура Decision Log

Назначение: **почему так решили** (смысловые решения).

Минимальные поля записи:

- `id`  
- `timestamp`  
- `project_id` / `task_id` (если есть)  
- `category` (`scope`, `rules`, `delivery`, `emergency`, `standards`, `accept_risk`, …)  
- `summary`  
- `rationale`  
- `decision`  
- `actors` (человек / роли ИИ как консультанты)  
- `evidence_refs[]`  
- `supersedes` / `superseded_by`  
- `status` (`active` | `superseded` | `archived`)

#### Структура Audit Log

Назначение: **что произошло** (факты событий).

Минимальные поля:

- `id`  
- `timestamp`  
- `actor` (user / system / ai_role)  
- `action` (`gate_confirmed`, `review_accepted`, `scope_frozen`, `ecp_started`, `standards_sync`, …)  
- `object_ref`  
- `before_ref` / `after_ref` (опционально)  
- `correlation_id` (связка с decision / emergency / task)  
- `integrity` (хэш записи / цепочка)

Audit не заменяет Decision: «нажали кнопку» ≠ «почему».

#### Индексация

Обязательные индексы (логические):

- по `timestamp`;  
- по `project_id` + `task_id`;  
- по `category` / `action`;  
- по `correlation_id`;  
- по `status`;  
- полнотекст по `summary` (Decision).

Физическая форма (файлы/SQLite) — решение реализации позже; архитектурно индексы обязательны до роста > порога комфортного линейного чтения.

#### Архивирование

- Активный хвост: последние N дней или M записей в «горячем» хранилище проекта.  
- Архив: `.ai-pos/records/archive/YYYY/MM/...` (или эквивалент).  
- Архивирование не меняет `id` и не удаляет searchable metadata-индекс.  
- Hot + archive вместе дают полный историю.

Рекомендуемый порог старта архивации: когда hot-лог > согласованного размера/числа записей (значение — на подтверждение).

#### Периодические summary

- Автоматические summary **не удаляют** исходные записи.  
- Периоды: неделя / месяц / закрытие этапа.  
- Summary = производный документ со ссылками на `id` решений и ключевых audit-событий.  
- Статус summary: `derived`; пересчёт допустим; исходники первичны.

#### Правила ссылок и поиска

- Ссылки только по стабильным `id` (не по номеру строки).  
- Внешние документы ссылаются как `decision:<id>` / `audit:<id>`.  
- Поиск: сначала hot-индекс, затем archive-индекс.  
- Найденная `superseded` запись показывается с указателем на актуальную.

#### Когда запись считается superseded, но не удаляется

Запись становится `superseded`, когда:

1. принято новое решение по тому же вопросу (`superseded_by`);  
2. KEEP/SUPERSEDE закрыл ECP новым штатным решением;  
3. обновлены правила/scope версии, отменяющие смысл старого решения.

Правила:

- удаление запрещено в нормальном режиме;  
- правка текста исторической записи запрещена;  
- допустимы только добавление корректирующей записи или пометка superseded;  
- исключения (юридическое удаление) — вне v1, отдельным протоколом redaction с tombstone.

### Альтернативы

1. Один общий лог — проще, хуже разделяет «почему» и «что».  
2. Удалять старое через 30 дней — недопустимо для аудита контроля.  
3. Хранить всё только в UI localStorage — не масштабируется и плохо для handoff.

### Риски

- Смешение Decision и Audit.  
- Огромные вложения в evidence без ссылочной модели.  
- Summary начнут считать источником истины вместо исходников.

### Критерий готовности

- Разведены Decision Log и Audit Log.  
- Поля минимального контракта зафиксированы.  
- Есть правила index / archive / summary / supersede.  
- Запрет удаления/молчаливой переписи зафиксирован.  
- Ссылки по `id` обязательны.

### Решения, требующие нашего подтверждения

1. Пороги архивации (дни / число записей / размер).  
2. Хранилище v1: JSONL в `.ai-pos/records/` или сразу SQLite?  
3. Нужны ли периодические summary автоматически или только по кнопке человека в v1?
